# 최종 정밀 검수

## 단계와 범위

1. 1차 번역: 원문을 한국어로 옮긴 단계.
2. 초벌 검수: 번역 후 원문과 인접 문맥을 다시 대조한 단계.
3. 최종 정밀 검수: 위 두 단계가 끝난 현재 번역본에서 남은 의미·표현·말투 문제를 확인하는 단계.
4. 기술 검증과 배포: 누락·태그·수치·레이아웃·캐시·CDN 상태를 검증하는 별도 단계.

이미 끝난 단계를 다시 시작하지 않는다. 자연스럽고 정확한 번역은 유지하고 근거 있는 문제만 수정한다. 자동 검사 통과는 문맥 검수 완료가 아니며, 파일을 수정하지 않았어도 실제로 읽은 범위는 검수 기록에 남긴다. 정밀 검수 요청을 CDN 게시 승인으로 간주하지 않는다.

## 시작 기준 고정

- 장기 전수 검수는 `../reviews/final-review/README.md`와 `../reviews/final-review/NEXT.md`를 먼저 확인하고 `node scripts/final-review-progress.mjs status`로 재개 위치를 읽는다. 변경 없는 `completed` 범위는 건너뛴다. 실제 읽은 30~50개 메시지마다 체크포인트를 저장하며, 지시서 변경만으로 완료 이력을 지우거나 전체를 재검수하지 않는다.

- 기존 검수 기록과 후속 수정 커밋을 확인하고, 대상 시나리오 ID·포함/제외 범위·진행 단계를 먼저 기록한다.
- 원본 캐시/인덱스 SHA256, 저장소 기준 커밋과 미커밋 변경 유무, 대상 번역 파일의 검수 전 SHA256, 읽은 지시서·캐릭터 카드·용어집의 경로와 SHA256을 기록한다.
- 과거 기록의 해시와 현재 해시가 다르면 후속 변경을 대조한다. 그 차이만으로 번역 불량이나 초벌 검수 미실시라고 판정하지 않으며, 이전 기록의 해시를 덮어쓰지 않는다.
- 재개 시 위 기준의 변경 여부를 확인한다. 원문·화자·등장 순서·번역이 실제로 바뀌었다면 해당 변경과 관련 문맥만 별도 확인한다. 지시서 보강만으로 이미 정밀 검수를 완료한 번역을 다시 읽지 않으며, 읽지 않은 나머지에 완료 표시를 전파하지 않는다.
- 원본 캐시 경로나 바이트가 바뀌거나 이전 경로가 사라지면 새 FIRST에 현재 원본을 고정하고 배정된 대상 필드를 다시 대조한다. 선택 필드의 일치와 과거 전체 캐시의 일치는 별도로 기록하며, 다른 원본에서의 통과로 기존 원본 불일치 보류를 해제하지 않는다.

## 완료분 보존 정책 (2026-09-06 사용자 결정)

- 이번 보강 규칙은 앞으로 번역·검수할 미완료분에 적용한다. 기존 정밀 검수 완료분은 재검수할 필요가 없다는 사용자 결정을 우선한다. 과거 규칙 버전으로 완료한 항목도 지시서 차이만으로 다시 검수하지 않는다.
- `completed`뿐 아니라 내용이 그대로인 기완료 `rule-impact-check`도 중복 작업 큐에서 제외한다. 이 도구 표시는 해시 차이의 기록이며, 이번 개정에 따른 의무 재검수 지시가 아니다. 기존 영수증과 해시를 새 값으로 바꾸거나 새 검수 실적을 발급하지 않는다.
- 부분 검수의 이미 승인된 위치도 보존한다. 원문·화자·명령·위치·저장 값의 대응 증거와 기존 보고서를 이어받고 신규 검수 실적은 0으로 기록한다. 실제 미검수 위치 및 미해결 보류만 다음 대상이다.
- 원문/번역의 후속 실질 변경이나 새로 확인된 구체적인 결함은 별도 작업으로 구분한다. 보류·제외·미검수 범위를 완료로 올리거나 화면·CDN 검증을 면제하지 않는다.
- 개정 전 상태, 개정 전후 지시서 해시, 기존 완료 증거와 적용 범위를 인수인계에 연결한다. 현재 상태 도구가 규칙 차이로 완료 수를 다르게 표시해도 이미 수행한 정밀 검수가 취소된 것은 아니다.

## 누락과 중복 등장

- 누락 검사의 단위는 다섯 명령(`message`, `dotmessage`, `messageTextCenter`, `messageTextUnder`, `l2dmessage`)에서 추출한 정확한 원문 고유 key다. 다섯 집합의 합집합에 있는 key가 번역 사전에 모두 있어야 한다. 원본 TextAsset의 명령 수·등장 순서와 인덱스를 대조하며, 인덱스 완료나 일본어 잔존 0만으로 원본 전체 완료를 주장하지 않는다. 의도적으로 유지한 이전 버전 호환 key는 별도 집합으로 기록한다.
- 문맥 검사의 단위는 원문 실행 순서의 메시지 등장이다. 예를 들어 메시지 100회에 고유 key 97개라면 key 97개를 대조하고 등장 문맥 100회를 읽는다. 동일한 대사라고 반복 장면을 생략하지 않는다.
- 화자는 시나리오 파일명이나 JSON 인접 항목으로 추측하지 않고 원본 메타데이터로 확인한다. 선택지·분기·회상·장면 전환이 있으면 해당 실행 문맥을 포함한다.
- 동일 key에 다른 화자·호칭·의미가 요구되면 공유 값 하나로 모두 자연스럽게 표현할 수 있는지 확인한다. 불가능하면 문맥별 조회 지원이 필요한 기술 문제로 남긴다. JSON에 중복 key를 만들거나 원문 key를 바꿔 해결한 척하지 않는다.
- 여러 캐시가 같은 시나리오 ID에 합쳐졌다면 캐시별 등장 순서를 먼저 복원한다. 서로 다른 파일의 행번호를 섞은 인덱스 순서를 사건 순서로 간주하지 않는다. 중복 대응은 명령·화자·원문·음성·캐릭터 슬롯과 캐시/행 위치로 증명하고, 다른 원문 변형은 보존한다. 대사 슬롯 일치만으로 캐릭터 리소스·연출·실행 결과까지 같다고 주장하지 않는다.
- 원본과 인덱스의 대응, 번역 사전의 고유 key 누락은 별도 검사다. 원본 대응이 통과해도 저장 key가 빠질 수 있다. 누락 key는 원본 근거로만 추가하며 첫 실패 보고서를 지우지 않고 수정 후 검증을 별도 보존한다. 사전 조사나 중복 매핑만으로 의미 검수 완료를 발급하지 않는다.

## 의미와 표현

- 남은 애매한 어휘만 `supplementary-reference.md`의 4순위 보조 자료로 확인한다. 기존 번역이 정확하면 유지하고, 단순한 사전 표현 차이를 오류로 판정하지 않는다. 실제 조회어·출처 버전/행·채택 또는 기각 이유를 기록한다. 조회하지 않은 자료를 참고했다고 주장하지 않는다.

- 문장 전체와 앞뒤 장면을 대조해 행동 주체·대상, 부정, 조건, 수량, 시간·인과관계, 확신/추측, 감정 강도가 유지되는지 확인한다.
- `style-core.md`의 한국어 수사·단위·조사 규칙을 적용한다. 일반 서술의 `한 방울`과 UI의 `1개`, `Lv10`, `30%`, `20초`는 별도로 판단하며 수치를 바꾸지 않는다.
- 알려진 화자에게만 캐릭터 카드를 적용하고, 상대·장면·의도적인 말투 전환을 함께 확인한다. 이름 표기와 지정 호칭은 유지하되 존댓말/반말을 기계적으로 통일하지 않는다.
- 원문 오탈자, 시간 모순, 잘못된 화자 표시가 의심되면 근거와 불확실성을 기록한다. 근거가 부족하면 임의로 내용을 보완하지 않는다. 의도된 이름 오기나 말장난을 정상 이름으로 자동 교정하지 않는다.
- 폰트 회피용 동의어 치환은 사용하지 않는다. 기존의 정확한 `홍보`, `골치를 썩이다` 등을 반대로 일괄 치환할 이유도 없다.
- 공통 용어를 교정하면 그 용어가 포함된 런타임 혼합 key도 확인한다. 기존 수집 key는 호환용으로 보존하고, 교정된 이름으로 실제 조합될 새 key가 필요하면 추가한다. 원문 key 일괄 치환으로 대응하지 않는다.

## 레이아웃과 보호 요소

- 원문 key, 자리표시자, 비레이아웃 태그와 속성, 파일/음성 식별자는 보호한다. 줄바꿈은 예외로 한국어 의미 단위에 맞춰 0~1개로 재배치하며, 원문과 개수·위치를 같게 요구하지 않는다. 소설 ruby는 `tags-placeholders.md`의 특수규칙을 우선 적용한다. 불필요한 독음 제거와 의미 있는 본문/대체독음의 한국어 번역을 일반 태그 손실로 오판하지 않는다.
- 노벨 줄당 목표 34자, 35~36자 확인 대상, 36자 초과 또는 세 줄은 미해결 레이아웃 문제다. UI는 해당 화면 규칙을 따르며 이 노벨 규칙을 일괄 적용하지 않는다.
- 의미를 손상하지 않는 재구성으로도 맞출 수 없으면 정보를 삭제하지 말고 미해결 상태로 남긴다. 대화 명령을 임의로 나누거나 태그를 제거하지 않는다.
- 정적 글자 수만으로 화면 정상 여부를 확정하지 않는다. 변수 치환 후 이름 길이, 글자 크기, 자동 줄바꿈, 글리프, 잘림·겹침을 실제 화면에서 별도 확인하고 미확인은 명시한다.
- 부분 검수 파일의 전체 저장값 기술 검사 수는 승인 등장 수와 분리한다. 길이 주의는 key/등장 단위와 승인·보류·미검수 범위별 수를 표시하고, 서로 다른 단위의 수를 빼거나 기술 검사 통과를 의미 승인으로 합산하지 않는다.

## 기록과 완료

### 원본 경계와 외부 이름 증거 (2026-09-08)

- 원문 인덱스와 추출기의 일치는 실제 게임 메시지 경계의 증명이 아니다. `dotmessage` 대사 뒤 숫자 필드나 이중 쉼표가 key에 포함된 사례는 원본 행, 추출 규칙, 런타임 `Message` 값을 구분한다. 런타임 근거가 없으면 기존 key와 호환 key를 보존하고 기술 보류하며, 인덱스/key 수정으로 검사만 통과시키지 않는다. 원문 자체의 잘못된 닫기 태그도 임의 정상화하지 않는다.
- 메시지 화자명과 `charaload`의 최종 이름 필드를 별도로 대조한다. NPC/형태 별칭은 원본 로드 행, 캐시 해시, 기존 기본 이름과 수식어를 근거로 추가한다. 모든 objectload 이름이 화면에 표시된다고 가정하지 않는다. 대사 위치가 없는 이름 문제에 가짜 메시지 위치를 부여하지 않으며, 해결 기록은 현재 이름 값과 원본 증거 해시에 연결한다. 이름 보완은 대사/공통 신규 검수 실적으로 더하지 않는다.

### 병렬 통합 종료 확인 (2026-09-08)

- `writeStopped` 하나만으로 최종 인계를 확정하지 않는다. 담당자의 최종 통지, `integrationNeedsAttention` 해소, 보고서/영수증/저장 값의 최종 해시 일치를 확인한 뒤 통합한다.
- QA 이후 보고서 메타데이터만 바뀐 경우에는 변경 사유와 전후 해시를 별도 기록한다. 모든 배포 값과 검수 범위가 동일함을 입증한 경우에만 이전 QA를 유지하며, 번역 값/검사 코드/검사 입력이 바뀌면 관련 검사를 다시 실행한다. 이전 통합 기록은 덮어쓰지 않는다.

### 공통 기록 규칙

- 지시서 개정은 개정 전후 해시, 변경 규칙, 근거 회차, 적용 대상과 완료분 보존 결정을 별도 문서로 남긴다. 과거 영수증의 해시/완료 판정을 덮어쓰거나 새 규칙을 읽었다는 이유만으로 새 의미 검수 완료를 발급하지 않는다. `rule-impact-check`의 이번 보강 관련 항목은 위 사용자 결정에 따라 재검수하지 않는다. 부분 완료의 이전 범위도 별도로 보존하며 새 버전에서 자동 합산된다고 가정하지 않는다.
- 병렬 작업은 캐릭터별 소규모 파일 소유권과 FIRST를 먼저 고정한다. 종료 요청 시 현재 묶음만 통합하고 다음 묶음을 배정하지 않는다. 담당별 검수 후 main의 저장 값/원본/보고서 대조는 통합 검증이지 독립적인 두 번째 의미 검수가 아니다. 집중 검사는 각 묶음에, 전체 QA는 통합 후 한 번 수행하며 실패 수정으로 재실행하면 횟수를 별도로 남긴다.
- 검수 이력·순서·관계가 중요한 공통 교정은 고유 원문 수, 실제 수정 값 수, 저장 경로별 사본 수를 구분한다. 기완료 항목의 영향 수정은 신규 완료 실적에 다시 더하지 않는다.
- 실제로 읽은 범위 기록과 개별 수정/발견 판정을 구분한다. 읽지 않은 위치에 자동 `keep` 판정을 생성하지 않으며, 공유 key 한 번의 수정 근거가 여러 등장에 적용되더라도 각 등장 문맥을 읽은 근거는 필요하다. 통합 단계에서 정식 스키마에 없는 개별 `keep` 의무를 뒤늦게 추가하지 않는다. 최종 보고서에서 같은 위치의 모순된 초안 판정은 정리하되 원문 문제 근거와 이전 초안은 보존한다.
- 공통 사본은 `tags-placeholders.md`의 색상 사본 절차를 따른다. 과거 보류 집계는 정식 도구의 이력 정렬 규칙(없는 `recordedAt`은 빈 문자열)에 맞추고, 현재 규칙 버전의 보류와 모든 규칙 버전에서 남은 보류를 구분한다. 지시서 해시가 바뀌어 `hold`가 다른 영향 상태로 표시되어도 미해결 사유를 없애지 않는다.
- 도구 출력이 잘렸으면 보지 못한 범위는 검수한 것이 아니다. 읽기 범위를 줄여 다시 확인하고, 수정 후 실제 저장 값을 재독한 다음 `record`한다. 제안 초안과 최종 저장 값이 다르면 최종 보고서에 실제 값을 기록한다.
- 자동 검사 경고는 종류/위치/수치와 유지 근거를 기록한다. 기존 경고가 남은 성공 결과를 무경고로 보고하지 않으며, 실행하지 못한 검사도 통과로 세지 않는다. 같은 검수자의 원문 대조와 재독은 독립 2인 검수로 표시하지 않는다.
- QA 실행 전후에 각 검사가 실제 사용한 캐시·MasterData·수집본의 경로와 SHA256을 대조하고 실행 결과에 연결한다. 로컬 `Config/master.json`을 사용한 검사와 현재 다운로드 캐시·실시간 수집본을 읽은 검사를 구별한다. 사후에만 확보한 해시는 사후 포착으로 표시하며 최초 실행의 입력 증거로 소급하지 않는다.
- 실행 중 QA 입력이 바뀌면 첫 결과를 보존하고 해당 입력을 고정해 관련 검사를 다시 실행한다. 이전 실패와 새로 관측된 누락, 이번 수정의 회귀는 실제 입력과 변경 전후 사전·동적 템플릿을 대조해 구분한다. 이전 입력을 확보하지 못했으면 정확한 최초 발생 시각을 단정하지 않는다. 이전과 같은 실패라고 전체 QA를 통과로 표시하거나 정적 번역 key를 임의로 추가해 덮지 않는다.
- 원문 불명확, 기술 문제, 검수에서 다룰 수 없는 콘텐츠는 사유별로 보류한다. 특정 부분이 보류되어도 분리 가능한 일반 대사는 계속 검수할 수 있지만 보류 부분이나 파일 전체를 완료로 올리지 않는다.
- 사용자가 오늘 작업 종료를 요청하면 현재 합의한 구간만 마무리하고 완료/부분/보류/대기, 다음 ID·위치, 검사·화면·배포 여부를 재개 문서에 저장한다. 이전의 계속 진행 요청이나 과거 머리말보다 최신 중단 요청을 우선한다.

- 항목별 기록: `novelId`, 원본 등장 위치/명령/화자, 정확한 `sourceKey`, 수정 전·후 번역, 문제 유형, 근거, 판정(`수정`, `유지`, `보류`), 재검수한 인접 범위.
- 회차별 기록: 기준 버전/해시, 메시지 등장 수와 고유 key 수, 실제 읽은 범위, 제외·보류 항목, 자동 검사 명령/결과, 검수 후 파일 SHA256, 화면 확인 여부.
- 저장된 API 검수 완료 상태는 그 입력 버전에만 유효하다. 고유 key와 JSON 순서만 검토한 도구 결과를 화자별 중복 등장까지 확인한 전수 검수로 표시하지 않는다.
- 의미 수정 후에는 해당 문맥을 다시 읽고, 기존에 커밋된 파일도 명시적 `--file` 범위로 레이아웃을 검사한다. 변경 파일 0개인 `--changed` 결과는 검수 증거가 아니다.
- 맞춤법만 고친 경우에는 정확한 기계적 변경 범위와 기술 검사 결과를 기록하며, 해당 파일 전체를 새로 의미 검수했다고 주장하지 않는다.
- 포함 범위의 미해결 blocking 문제가 없어야 완료다. 이미 승인된 제외는 정확한 ID와 함께 보존하고 전체 완료로 확대하지 않는다. 번역·문맥 검수·기술 검사·게임 화면·CDN 게시의 완료 여부는 구분하여 보고한다.
